# План: управляемый и прозрачный copilot для LogiCore Agent

Статус: планируется. Документ описывает целевую доработку, а не текущие возможности.
Текущая архитектура агента описана в [DEV.md](DEV.md), только невыполненные работы —
в [ROADMAP.md](ROADMAP.md).

## Цель

Получить интерфейс, в котором аналитик может:

- видеть фактические переходы между графами, агентами и инструментами;
- просматривать промпт, входную задачу, сообщения, tool calls и результаты каждой роли;
- получать результаты инструментов в табличном виде;
- вручную приостанавливать работу без обязательных approval-интерраптов;
- исправлять задачу, план и отдельные параметры запуска;
- добавлять контролируемые read-only вызовы инструментов;
- продолжать работу от предыдущего checkpoint, создавая новую ветку расследования.

Основной принцип: **Aegra — единственный execution backend**, AG-UI — протокол для UI,
CopilotKit — интерфейс. Redis напрямую не используется.

## 1. Перевести AG-UI sandbox на Aegra

### Изменения

Переработать `agui-agent/app.py`:

- убрать `build_graph(checkpointer=InMemorySaver())`;
- убрать второй in-process экземпляр графа;
- принимать AG-UI `RunAgentInput`;
- создавать или открывать Aegra thread по `threadId`;
- запускать граф `agent` через `POST /threads/{thread_id}/runs/stream`;
- преобразовывать Aegra SSE в AG-UI события.

Вынести логику из `app.py`:

```text
agui-agent/
├── app.py              # HTTP endpoints
├── aegra_client.py     # threads, runs, state, history, cancel
├── agui_mapper.py      # Aegra events → AG-UI events
└── control.py          # pause, edit, checkpoint, resume
```

При запуске использовать:

- `assistant_id=agent`;
- `stream_subgraphs=true`;
- `durability=sync` для управляемых запусков;
- `multitask_strategy=reject`, чтобы два UI не запустили конкурирующие runs в одном треде.

`copilotkit-demo` продолжит подключаться к `/agent` через `HttpAgent`, поэтому его
протокол подключения почти не изменится.

### Результат

- Run из CopilotKit виден в Aegra.
- Состояние сохраняется в PostgreSQL.
- После перезапуска `agui-agent` и браузера расследование не теряется.
- Основной UI и CopilotKit могут открывать один и тот же thread.
- Второго движка расследований больше нет.

## 2. Сделать единую модель наблюдения выполнения

Ввести внутренний UI-контракт `ExecutionEvent`:

```text
ExecutionEvent
├── event_id
├── thread_id / run_id
├── checkpoint_id / checkpoint_ns
├── graph_path          # supervisor → deep → item-3
├── node                 # planner / investigator / tool
├── role                 # scout / investigator / reporter
├── work_item_id
├── event_type
├── timestamp
├── status
├── payload_ref
└── parent_event_id
```

Типы событий:

- `graph_entered`, `graph_finished`;
- `node_started`, `node_finished`;
- `model_called`, `model_responded`;
- `tool_requested`, `tool_finished`;
- `checkpoint_created`;
- `state_edited`;
- `run_paused`, `run_resumed`, `run_cancelled`;
- `error`.

Не добавлять полные prompt/result payloads в checkpoint без необходимости: сотни
вызовов иначе чрезмерно раздуют state. Для UI нужна пагинация и компактные представления.

### Отображение

В `copilotkit-demo` разделить представления:

1. **Обзор** — текущая задача, активный узел, план, гипотезы, находки.
2. **Выполнение** — дерево графов и вызовов, фильтры и поиск.
3. **Доказательства** — существующие таблицы Evidence.
4. **Отчёт** — итоговый Markdown и артефакты.
5. **Состояние** — структурированные поля state, diff между checkpoints, без огромного
   сырого JSON на основном экране.

Для длинных расследований:

- виртуализация или постраничная загрузка событий;
- фильтр по роли, work item, инструменту и статусу;
- режим «только ошибки»;
- сворачивание завершённых веток;
- быстрый переход «к активному узлу».

## 3. Показать фактическую работу каждого агента

Для Scout, Investigator и Reporter сделать карточку исполнения:

```text
Scout
├── Модель
├── Исходная задача
├── Эффективный system prompt
├── Динамический контекст
├── Входные сообщения
├── Доступные инструменты
├── Tool calls и Evidence
├── Structured response
└── Длительность и токены
```

### Изменения в агенте

Добавить наблюдение через официальные LangChain middleware:

- фиксировать фактический prompt после `dynamic_prompt`;
- связывать событие с `run_id`, ролью и work item;
- передавать model input/output как наблюдательные события;
- не менять сами промпты и маршрутизацию;
- не раскрывать скрытые reasoning traces — только фактические сообщения, инструменты
  и structured output.

Приватные каналы `scout_msgs`, `inv_msgs`, `rep_msgs` остаются источником истории
сообщений. В публичный `messages` tool-циклы не переносятся.

### Графическое представление

Получать топологию из:

- `/assistants/agent/graph`;
- `/assistants/agent/subgraphs`.

Поверх топологии отображать:

- активный узел;
- завершённые и failed-узлы;
- текущий путь выполнения;
- вложенные графы;
- параллельные work items;
- количество событий и вызовов в каждом узле.

Дерево работы и топология графа остаются разными режимами: первое отвечает «что
исследуем», второе — «где сейчас находится исполнение».

## 4. Реализовать pause, редактирование и resume

### Режимы работы

Сохранить два режима:

- **Автопилот** — текущее поведение, агент никого не ждёт.
- **Пошаговый режим** — остановки на явно выбранных границах.

Отдельная кнопка «Пауза» доступна в обоих режимах. Обязательных approval-интерраптов нет.

### Pause

Использовать Aegra:

- `interrupt_before` — перед выбранным узлом;
- `interrupt_after` — после выбранного узла;
- `/runs/{run_id}/cancel` — для остановки уже выполняющегося run.

UI различает статусы:

```text
Запрошена пауза → Останавливается → Paused
```

Нельзя показывать `Paused` только потому, что браузер оборвал SSE.

### Редактирование состояния

Не начинать с произвольного JSON. Сначала поддержать безопасные формы:

- задача расследования;
- цель и acceptance work item;
- зависимости и порядок этапов;
- активное окно;
- prompt override для конкретной роли;
- выбор checkpoint для продолжения.

Backend проверяет изменения через существующие Pydantic-контракты:

- уникальность ID;
- корректность зависимостей;
- допустимые статусы;
- ограничения required/optional;
- существование Evidence ID;
- запрет изменения уже выполненных фактических tool results.

Сохранение выполняется через Aegra `POST /threads/{thread_id}/state` с `checkpoint_id`
и, где необходимо, `as_node`.

### Prompt override

Добавить отдельный run-scoped канал настроек, например:

```text
control_overrides.scout.prompt
control_overrides.scout.task
```

`dynamic_prompt` применяет override только в выбранной области. Каждое изменение
фиксируется:

- исходное и новое значение;
- автор действия;
- время;
- checkpoint;
- причина.

Файлы промптов из UI не перезаписываются.

## 5. Сделать откат через ветвление checkpoints

Сценарий:

1. Пользователь открывает историю checkpoints.
2. Видит узел, время, состояние плана и накопленные Evidence.
3. Выбирает «Продолжить отсюда».
4. Просматривает diff и при необходимости редактирует state.
5. Запускается новый run с `checkpoint_id`.

История не удаляется и не перезаписывается:

```text
C1 → C2 → C3
      │
      └── C2′ → новый run
```

В интерфейсе сохраняются `parent_checkpoint_id` и связь веток.

Отдельно предупреждать: откат state не отменяет уже отправленный callback, созданный
S3-файл или запись в Context Memory.

## 6. Добавить ручные вызовы инструментов

На паузе пользователь сможет:

- выбрать разрешённый read-only MCP-инструмент;
- заполнить форму аргументов;
- увидеть сформированный запрос и окно;
- выполнить вызов;
- получить результат в той же таблице Evidence;
- продолжить run с этим Evidence.

Backend должен использовать существующую нормализацию `EvidenceRecord`. Запрещено
подделывать `ToolMessage` или вставлять результат, которого фактически не было.

Произвольный код, SQL и неразрешённые MCP-инструменты не добавляются.

## 7. Добавить пошаговость внутри агентов отдельным этапом

Сначала поддержать паузу на существующих границах:

- после Intent;
- после Scope;
- после Planner;
- до и после Scout;
- до и после work item;
- до и после Reporter.

Затем отдельно решить более мелкую гранулярность `model → tool → model`.

Сейчас `create_agent` выполняет внутренний цикл одним `ainvoke`, а deep-волны
собираются внутри `execute`. Поэтому checkpoints между каждым tool call автоматически
не появятся.

Для полной пошаговости:

- проверить использование checkpointer у `create_agent`;
- использовать штатные LangGraph checkpoint/namespace primitives;
- не создавать новый граф только ради UI;
- сохранить существующие item-subgraphs и семантику параллельных волн;
- покрыть продолжения после tool limit отдельными тестами.

## 8. Проверки

### Unit и integration

- преобразование Aegra events в AG-UI без дублей и потерянных ID;
- восстановление событий после reconnect;
- отмена run меняет фактический статус в Aegra;
- проверка редактируемого плана Pydantic-схемами;
- запрет некорректных зависимостей и Evidence ID;
- prompt override применяется только к нужной роли;
- ручной tool call создаёт настоящий `EvidenceRecord`;
- запуск от checkpoint не дублирует старые Evidence;
- пагинация сотен событий без потерь.

### UI

- TypeScript typecheck;
- production build;
- synthetic run с сотнями вызовов и десятками work items;
- компактное отображение при широком и узком экране.

### Live-сценарии

1. «Привет» — run появляется в Aegra и переживает перезапуск UI.
2. Проверка последнего часа LogiCore — видны Scout, фактический prompt, IQL и таблица Evidence.
3. Пауза после Planner — редактирование плана и успешный resume.
4. Откат на checkpoint — создана новая ветка, прежняя история сохранена.
5. Остановка активного run — Aegra подтверждает cancelled/paused статус.
6. Основной чат `:3000` продолжает работать без изменений.

Полный regression-набор `tests/`, `git diff --check` и live API остаются обязательными.

## Порядок реализации

1. **Aegra adapter вместо in-process графа.**
2. **Единый execution event stream и восстановление после reconnect.**
3. **Прозрачность агентов: prompts, messages, tools, graph topology.**
4. **Pause/resume и редактирование плана на безопасных границах.**
5. **Checkpoint branching и prompt overrides.**
6. **Ручные tool calls.**
7. **Пошаговость внутри `create_agent`.**

Такой порядок сначала устраняет главную проблему — раздельные runtime — и только затем
добавляет управление. Иначе кнопки pause/edit/rollback остались бы визуальной имитацией
поверх неподходящего backend.

## Принятые допущения

- Интерфейс остаётся локальным single-user; OIDC/multiuser не добавляется.
- Пауза выполняется только по явному действию пользователя или в выбранном пошаговом режиме.
- Откат означает новую ветку от checkpoint, а не удаление истории или отмену внешних side effects.
- Ручные инструменты ограничены существующими read-only MCP-операциями.
- Redis остаётся внутренним брокером Aegra и не становится API интерфейса.
