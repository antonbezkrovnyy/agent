# Дальнейшее развитие агента

Этот документ содержит рекомендации по следующим этапам. Он не описывает уже
реализованный функционал и не является обязательным планом с фиксированными сроками.
Текущая архитектура и контракты приведены в [DEV.md](DEV.md).

## Общая оценка

Агент представляет собой рабочую исследовательскую систему, а не просто цепочку
промптов: есть маршрутизация, Evidence, критики, память, воспроизводимые отчёты и
внешний MCP-интерфейс. Сейчас важнее измерить и повысить качество анализа, чем
добавлять новых агентов, хранилища или сложность графа.

Главный риск — слишком категоричные выводы при ограниченных данных. Например, по
двум heartbeat-событиям за 15 минут агент назвал активность аномально низкой без
сравнения с базовой линией. Такой отчёт формально содержит Evidence, но аналитический
вывод всё равно недостаточно обоснован.

## 1. Набор оценочных сценариев

Приоритетная задача — собрать 20–30 репрезентативных сценариев на реальных или
зафиксированных тестовых данных:

- обзор периода и подсчёт событий;
- поиск первого наблюдаемого появления;
- event drilldown и entity pivot;
- continuation и изменение временного окна;
- ложная аномалия и недостаток данных;
- неполные и ошибочные ответы инструментов;
- отчёт, выгрузка и работа через внешний MCP.

Проверять нужно не только успешное завершение run, но и:

- корректность выводов и их категоричность;
- фактические IQL-запросы и временные окна;
- соответствие claims содержимому Evidence;
- полноту limitations и `NOT_CHECKED`;
- отсутствие выводов, не подтверждённых свежими данными.

По этим сценариям следует сравнивать модели и изменения промптов. Unit-тесты графа
не заменяют такую оценку качества.

## 2. Более строгие аналитические ограничения

Категоричные утверждения должны требовать специальных проверок:

| Утверждение | Что необходимо проверить |
|---|---|
| «Аномально» | Базовая линия или сопоставимые периоды |
| «Впервые появилось» | Достаточная глубина поиска и граница наблюдения |
| «Причина» | Исключение основных альтернативных объяснений |
| «Поток отсутствует» | Корректный фильтр, окно и контроль наличия источника |

Часть требований можно проверять детерминированно до выдачи отчёта. LLM-критик
остаётся дополнительной проверкой, а не единственной защитой от необоснованных выводов.

## 3. Контроль полного времени выполнения

Сейчас `AGENT_TIMEOUT_SECONDS` ограничивает отдельный `create_agent.ainvoke`, но не
весь run с Intent, критиками и консолидацией памяти.

Следующий этап:

- собирать длительность каждого этапа и долю ожидания LLM/MCP;
- определить наблюдаемые SLO для quick и deep;
- добавить общий технический предел run с сохранением текущего state;
- при остановке возвращать собранные Evidence и явные limitations.

Пользовательский выбор бюджета времени и approval-interrupts не требуются.

## 4. Укрепление внешнего MCP

Базовый асинхронный контракт уже работает. Для полноценного agent-to-agent использования
остались следующие улучшения:

- continuation существующего расследования без создания нового треда;
- настоящий MCP `structuredContent` и output schemas вместо JSON только в text content;
- повторный запуск после отмены и понятные состояния ошибок;
- проверка потери соединения с Aegra и восстановления клиента;
- обновление истёкших ссылок и повторное скачивание старых пакетов;
- согласованная модель доступа при выходе за пределы локального single-user режима.

A2A можно рассматривать позже поверх того же сервиса. ACP не требуется.

## 5. Консолидация работы с артефактами

Создание и обновление файлов распределено между reporting tools и `memory_save`.
Их следует объединить в один предметный сервис с единым результатом:

- Markdown с цепочкой расследования и аудитом памяти;
- ZIP с согласованными `report.md`, Evidence и manifest;
- object keys и метаданные в state;
- свежие подписанные URL только при выдаче.

Это снизит риск выдать отчёт без аудита или пакет с устаревшим содержимым.

## Что пока не требуется

- новые субагенты и дополнительные уровни графа;
- вторая СУБД или другой investigation engine;
- автоматическое сравнение и переписывание skills;
- расширение памяти без оценки качества извлечения;
- A2A без конкретного потребителя;
- OIDC/multiuser в текущем локальном режиме.

## Рекомендуемый порядок

1. Оценочные сценарии и измерение качества.
2. Ограничения на необоснованные аналитические выводы.
3. Наблюдаемость и общий технический timeout run.
4. Продолжение и строгие схемы внешнего MCP.
5. Консолидация артефактов и последующее развитие A2A при необходимости.
