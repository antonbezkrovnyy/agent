## Что стало лучше

### Именованные конструкции

Модель вынесла повторно используемые элементы в понятные определения:

| Конструкция | Назначение |
|---|---|
| `SYSLOGPRI` | PRI в угловых скобках |
| `SYSLOGTIMEWITHYEAR` | Timestamp с годом |
| `ORIGINADDR` | IP или hostname |
| `MNEMONIC` | Vendor tag, severity и msg_id |
| `ACLHEAD` | ACL, действие и протокол |
| `SRCENDPOINT`, `DSTENDPOINT` | Вложенные endpoint-конструкции |
| `HITBLOCK` | Счётчик и маркер |
| `HEXTOKEN`, `HEXPAIR` | Непрозрачные hex-значения |
| `BODY106100` | Собранное тело Family |

Например:

```text
SYSLOGTIMEWITHYEAR = %{MONTH} +%{MONTHDAY} %{YEAR} %{TIME}
ACLHEAD = access-list %{NOTSPACE:acl_name} %{WORD:action} %{WORD:protocol}
BODY106100 = %{ACLHEAD} %{SRCENDPOINT} +%{FLOWARROW} +%{DSTENDPOINT} +%{HITBLOCK}(?: +%{HEXPAIR})?
```

Это уже можно читать и изменять как спецификацию парсера, а не как эссе о формате.

### Слои разбора

Грамматика разбита на последовательные шаги:

```text
envelope_pri
→ envelope_timestamp
→ envelope_origin
→ message_mnemonic
→ body_aclhead
→ body_src_endpoint
→ body_dst_endpoint
→ body_hitblock
→ body_hexpair
```

Каждый слой принимает capture предыдущего (`l1_rest`, `l2_rest` и так далее). Это соответствует стратегии конверт → payload и позволяет не создавать одну мега-регулярку.

## Обнаруженные ошибки

### 1. Удвоенный `%`

В `MNEMONIC` и `envelope_origin` модель использует `%%`:

```text
MNEMONIC = %%(?<vendor_tag>...)
... (?<l3_rest>%%.*)$
```

В исходной строке один `%`. Если модель хотела экранировать символ, такая запись всё равно будет искать два подряд и не совпадёт с RAW. Следует использовать `%` либо корректную escape-форму для выбранного Grok-runtime.

### 2. Выдуманный маркер

```text
HITMARKER = first hit|[0-9]+-second burst
```

В исходной постановке и предыдущих исследованиях рассматривался вариант `second interval`, а не `second burst`. Это пример недопустимой самодеятельности при построении статического маркера.

### 3. Исполнение ещё не проверено

Ответ прошёл Pydantic-валидацию JSON, но не компиляцию и не исполнение Grok на RAW. Поэтому остальные конструкции нельзя автоматически считать рабочими. Следующий этап должен проверить развертывание шаблонов и полное покрытие строки.
