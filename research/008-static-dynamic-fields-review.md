# R008 — классификация полей только static/dynamic

> Проверка упрощённой схемы без `derived`: структура Family отделяется от значений конкретного наблюдения. Ограничение закреплено как `Literal["static", "dynamic"]`.

## Краткий результат

**Формальное ограничение сработало: `derived` исчез, стратегия осталась компактной. Но модель ошибочно назначила `severity` как `static`, потеряла envelope-поля из `record_schema` и противоречит себе в обязательности портов и hit-маркера.**

| Dynamic | 11 |

## Что улучшилось

- Исчезла смешанная классификация `static/dynamic/derived`.
- `msg_id` корректно признан `static` внутри Family.
- `action`, `protocol`, ACL, endpoints и hit-count признаны `dynamic`.
- Стратегия содержит только решения, без обоснований и отвергнутых альтернатив.
- Схема сократилась с 20 до 13 полей.
- Рекурсивный разбор предлагается только при наблюдаемых маркерах вложенности.

## Проблемы результата

### 1. `severity` ошибочно назван `static`

```json
{
  "name": "severity",
  "category": "static",
  "source": "$.tag.severity"
}
```

Severity извлекается из конкретной строки и может меняться между событиями. По принятому правилу это `dynamic`.

`msg_id=106100` действительно может быть `static` **внутри выбранной Family**, но severity такой стабильностью не обладает.

### 2. `record_schema` потерял конверт

В `structure` модель выделила PRI, timestamp, host и тег, а в `strategy` потребовала сохранять RAW. Однако в `record_schema` отсутствуют:

- `raw`;
- `pri`;
- `timestamp`;
- `host`;
- `family/tag`.

В итоге схема описывает преимущественно тело сообщения, хотя по предыдущей договорённости конверт и payload должны быть разграничены, а не один из них выброшен.

### 3. Обязательность противоречит другим блокам

| Поле | В `record_schema` | В остальном ответе |
|---|---|---|
| `src_port`, `dst_port` | `required=true` | Порты названы опциональными |
| `hit_marker` | `required=true` | Квалификатор после hit-cnt назван необязательным |
| `raw` | Отсутствует | Стратегия требует хранить RAW неизменным |
| `opaque_ids` | Отсутствует | Структура содержит `$.body.flow_ref` |

Это показывает, что модель формирует блоки независимо и не проводит сквозную проверку их согласованности.

### 4. Static-поля не представлены как структурный контракт

В `record_schema` есть только два `static`: `msg_id` и ошибочный `severity`. Якоря `access-list`, `hit-cnt`, `first hit`, `->` остались в `structure`, но не вынесены в явный список статических элементов Family.

Если `record_schema` должен включать только смысловые значения, это допустимо, но тогда нужен отдельный контракт структуры. Сейчас граница между ним и `record_schema` не формализована.

## Оценка

| Критерий | Результат |
|---|---|
| Только `static/dynamic` | Выполнено формально |
| Правильная классификация | Частично: ошибка `severity` |
| Компактная стратегия | Выполнено |
| Сохранение envelope и payload | В `structure` есть, в `record_schema` потеряно |
| Согласованность обязательности | Нарушена |
| Минимальная схема | 13 полей, но неполная |
| Наблюдения отделены от гипотез | В основном да |

## Вывод

**R008 подтверждает, что одного ограничения enum недостаточно.** Модель использует только разрешённые категории, но всё ещё нуждается в явных правилах:

- `static` — стабильно внутри Family;
- `dynamic` — извлекается из наблюдения и меняется;
- `record_schema` должен сохранять и конверт, и payload;
- `required` должен согласовываться с особенностями формата;
- итоговый ответ нужно проверять на перекрёстную согласованность блоков.

Поэтому R008 — полезный диагностический эксперимент, но не замена R007 как baseline.
