# R006 — проектирование контракта парсера

> Переход от интерпретации события к стратегии парсинга, схеме записи, свойствам формата, граблям и интеграции. Parser code и тестовые кейсы по решению владельца не генерировались.

## Краткий результат

**Модель построила полный архитектурный черновик: двухслойный parsing pipeline, dispatch по `msg_id`, fail-open, плоская схема, производные ключи и метрики. При этом часть категорий полей и ECS-маппинга требует исправления, а многие свойства формата остались гипотезами.**

## Заданная структура

| Блок | Требование |
|---|---|
| `essence` | Смысл события для дежурной смены |
| `strategy` | Решение + обоснование + отвергнутые альтернативы |
| `record_schema` | `name / category / type / required / source` |
| `format_features` | Свойство формата + следствие для дизайна |
| `pitfalls` | Грабля + механизм поломки + лечение |
| `integration` | Стандартная схема, ключи дедупликации, метрики |

Отдельно требовалось различить:

- идентификатор сообщения, который определяет способ парсинга;
- идентификаторы события для дедупликации и корреляции;
- статические, динамические и производные поля;
- источник истины при конфликте PRI и мнемоники severity;
- `0` и отсутствие значения.

## Что предложила модель

### Стратегия

| Решение | Суть |
|---|---|
| Модель входа | Syslog-конверт → dispatch по `msg_id` → парсер конкретного тела |
| Диспетчер | `msg_class:msg_id`, а не поиск по свободному тексту |
| Контракт записи | Единая плоская схема + `raw_event`, `parse_success`, `reasons[]` |
| Ошибки | Fail-open: RAW сохраняется, отказ получает код и метрику |
| Нормализация | Типы и производные ключи в парсере; обогащение и корреляция downstream |
| Инструмент | Анкоренные regex и детерминированный scanner; критерии coverage, latency, throughput, поддержка |

У всех шести решений есть обоснования и отвергнутые альтернативы. Это соответствует заданной рамке: стратегия не сводится к выбору regex.

### Положительные проектные находки

- `msg_id` явно отделён от ключей события.
- Для дедупликации предложены разные `event_uid`, `dedup_key` и `correlation_key`.
- PRI severity и mnemonic severity хранятся раздельно, есть `severity_conflict`.
- Время разделено на `ts_raw`, `ts_local`, `ts_utc`, `ts_quality` и `year_source`.
- `0` и `null` различаются через `src_port_present` и `dst_port_present`.
- Для неизвестного хвоста предусмотрен `unmatched_tail`.
- Отказ получает и машинный `reason`, и метрику, и RAW для replay.

## Содержательные замечания

### 1. Категории полей местами неверны

| Поле | Модель | Замечание |
|---|---|---|
| `raw_event` | `static` | Должно быть `dynamic`: значение меняется на каждой строке |
| `action` | `derived` | Это непосредственно извлекаемое значение с ограниченным набором; требуется единое правило классификации |
| `event_class=acl_deny` | Единственное значение enum | Не согласуется с обязательным вариантом `permitted` |
| `ingest_source` | `dynamic` + гипотеза | Это транспортные метаданные, а не поле RAW; категорию нужно определить отдельно |

Следовательно, таблица есть, но классификация ещё не является согласованным контрактом.

### 2. Не все утверждения подтверждены

Модель честно пометила ряд свойств как гипотезы:

- варианты `first hit` и интервальной сводки;
- агрегированная семантика `hit-cnt`;
- назначение двух hashes;
- порт `0` у ASA;
- дополнительные хвосты `for user` и `by access-group`;
- возможность hostname вместо IP.

Это корректное поведение при нехватке доказательств, но такие поля нельзя публиковать как подтверждённую схему без отдельной проверки.

### 3. Правило severity смешивает независимые понятия

В `pitfalls` модель связывает изменение facility с расхождением `severity_pri` и мнемоники. Facility и severity — независимые компоненты PRI. Релей или несогласованная конфигурация действительно может изменить PRI, но сама смена facility не объясняет конфликт severity. Правило источника истины нужно формулировать заново.

### 4. ECS-маппинг требует независимой проверки

Примеры спорных соответствий:

- `@timestamp` предложено связать с ingest time, хотя это поле обычно относится ко времени события;
- `event.created` предложено связать со временем события, а не создания записи;
- `event.outcome=denied` и `event.type=denied` требуют проверки допустимых ECS-значений;
- `event.duration` получает секунды без приведения к принятой ECS-единицы;
- `network.direction=inbound` назван эвристикой, но всё же включён в итоговый маппинг.

Наличие названий ECS-полей не подтверждает корректность интеграции.

### 5. Объём и доказательность

JSON содержит около 40 КБ и 52 поля для одной строки. Это полный архитектурный brainstorm, но не минимальный контракт. Источники не привязаны к отдельным решениям, поэтому проверять его придётся вручную или следующим evidence-контуром.

## Оценка по критериям

| Критерий | Оценка |
|---|---|
| Стратегия, а не пересказ regex | Выполнено |
| Отвергнутые альтернативы | Есть у всех решений |
| Единый контракт записи | Есть, требует сокращения и уточнения |
| Классы полей | Формально есть, содержательно местами неверны |
| Особенности со следствиями | Выполнено |
| Грабли с механизмом и лечением | Выполнено, отдельные механизмы спорны |
| Parser code и тесты | Не генерировались |
| Evidence на уровне решений | Отсутствует |
| Production-готовность | Не достигнута |

## Вывод

**R006 полезен как сильный архитектурный черновик и чек-лист для последующего проектирования.** Наиболее ценны разделение dispatch/identity, fail-open, явные производные и различение `0/null`.

Принимать схему из 52 полей и ECS-маппинг как готовый контракт нельзя: сначала нужно сократить состав, исправить классификацию и подтвердить свойства формата источниками.
